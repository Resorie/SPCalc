# 更新官方版本或赛季

数据来源与核对目标是官方活动和 PRTS。复刻的导出数据及引擎是实现基础，不能把导入成功等同于原版规则已验证。当前只支持固定的 Stronghold-Protocol 数据格式。

1. 对照官方公告与 PRTS，列出本次新增、删除或调整的干员、技能、模组、装备、盟约、地图和战斗机制。取得上游生成数据，或将官方／PRTS 资料转换成同样的规范 JSON；不要直接复制网页文本当作引擎数据。
2. 把旧清单复制到临时文件，修改 `id`、`revision`、`label`、来源、采集日期和默认配置。每次发布使用新的目录 ID，保留旧快照以便旧配置复算。清单内的引擎 ID 必须与实际核对的代码一致。
3. 只有数值变化、且现有行为代码适用时，复用当前引擎适配器。若增加新技能机制或改变结算顺序，需要保留旧引擎，接入新的适配器并在 `src/engine.js` 注册独立 ID。新增数据格式需要新的适配层，不能绕过兼容性检查。
4. 先检查再导入，脚本会重算 SHA-256，验证结构、引擎和默认配置，不覆盖已有目录，也不自动切换默认版本：

```sh
node scripts/import-ruleset.mjs /path/to/normalized-data /path/to/new-manifest.json --check
node scripts/import-ruleset.mjs /path/to/normalized-data /path/to/new-manifest.json
```

5. 为改变的机制补充测试；至少核对干员两种形态、自选等阶、潜能／练度、模组、装备可用性、盟约成员与叠层。对关键配装记录官方可复查的对照条件。若当前靶场无法表达必要条件，标明不支持，不填入猜测结果。
6. 检查新旧规则包交替运行不串用数据，旧配置仍指向旧版本；通过测试后再修改 `data/catalog.json` 的 `default`（单人）及 `teamDefault`（团队），执行 `npm test` 和 `npm run build`。发布需要单独执行；导入脚本不联网、不发布。

`manifest.json` 的 `files` 只引用同目录 JSON；数据包不能指定执行任意 JS。代码实现仍受其固定引擎的支持范围约束。对上游的 `[ASSUMED]` 和已知差异，应逐项保留、核对和记录，不用一个“测试通过”替代机制准确性说明。

团队规则包还需声明 `files.stages`、`defaults.team` 和 `defaults.teamScene`：启用地图及其地形／机关／环境参数、默认队员配置、默认地图与靶子位置均放在数据中。为地图合法部署、治疗与生存、共享元素爆发及补弹、盟约计数与覆盖、站位特质、旧配置转入补充验证。地图数据变化不可只更新 UI 图形；必须同步传给战斗引擎。

若另有新版图标或地图素材，清单可通过 `iconSet` 和 `boardSet` 引用对应名称的本地索引，按新包单独生成，并保留旧版索引。若单人到团队需要使用不同的数据目录，在目录清单的单人条目中登记 `teamVersion`。普通访问读取默认版本，分享链接按其中的版本和规则键加载。
